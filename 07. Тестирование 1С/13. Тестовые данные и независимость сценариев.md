> [!abstract] Коротко
> Автотест должен давать **одинаковый результат при каждом запуске** и **не зависеть от других тестов**. Для этого нужны **известные тестовые данные**: эталонная тестовая база, которую восстанавливают из `.dt` перед прогоном; данные, которые сценарий создаёт **сам** в начале (с уникальными именами); или откат изменений (транзакция в модульных тестах). Сценарий не должен опираться на результат другого сценария и на «случайные» данные базы. «Мигающий» тест — то проходит, то падает без изменений в коде — почти всегда признак зависимости от данных, времени или порядка запуска.

## Почему тесты «ломаются сами»

Типичная история: в понедельник все сценарии зелёные, во вторник половина красные — хотя код никто не менял. Причины почти всегда в **данных**:

| Что случилось | Почему тест упал |
| --- | --- |
| Сценарий А провёл накладную на 3 чайника | Сценарий Б ждал остаток 10, а увидел 7 |
| Кто-то переименовал покупателя «Ромашка» | Шаг «выбираю по строке 'Ромашка'» ничего не нашёл |
| Вчерашний прогон упал на середине и оставил документ | Сегодня в списке на строку больше |
| Сценарии запустили в другом порядке | Б выполнился раньше А, которого он неявно ждал |
| Тест проверяет «сегодняшнюю дату» | В полночь дата сменилась |

Тест, который то проходит, то падает без изменений в программе, называют **нестабильным** или «мигающим» (flaky). Ему перестают доверять — и смысл автотестов пропадает.

## Три правила независимости

1. **Известные данные на старте.** Перед тестом база находится в заранее известном состоянии.
2. **Тест не зависит от других тестов.** Любой сценарий можно запустить отдельно и в любом порядке.
3. **Тест не портит данные для следующих.** После себя он либо убирает изменения, либо создаёт данные так, что они никому не мешают.

## Способ 1. Эталонная тестовая база

Самый простой и надёжный подход для UI-тестов:

```mermaid
flowchart LR
    A["Эталонная выгрузка<br/>Купец_тест.dt<br/>с известными данными"] -->|перед прогоном<br/>загрузить| B["Тестовая база"]
    B --> C["Прогон всех<br/>сценариев"]
    C -->|база «испачкана»| D["Следующий прогон:<br/>снова загрузить .dt"]
    D --> B
```

1. Один раз готовим тестовую базу с **минимальным известным набором** данных: 3 товара, 2 покупателя, 1 склад, приход 10 чайников.
2. Выгружаем её в файл `Купец_тест.dt` и храним рядом с тестами.
3. **Перед каждым прогоном** загружаем `.dt` в тестовую базу ([[01. Основы конфигурирования/28. Резервные копии и обслуживание базы|28. Выгрузка и загрузка]]). Все сценарии стартуют с одинаковых данных.

| Плюсы | Минусы |
| --- | --- |
| Просто и понятно | Эталон нужно обновлять при изменении структуры конфигурации |
| Ожидаемые числа известны заранее | Загрузка `.dt` занимает время |

## Способ 2. Сценарий создаёт данные сам

Сценарий в начале **создаёт** всё, что ему нужно: товар, покупателя, приход. Тогда он не зависит от того, что лежит в базе.

```gherkin
Сценарий: Остаток уменьшается после продажи
	# Подготовка: свой товар с уникальным именем
	Дано я создаю товар с наименованием "Чайник-тест-0412-1530"
	И я провожу приход 10 штук товара "Чайник-тест-0412-1530"
	# Действие
	Когда я провожу расходную накладную на 3 штуки товара "Чайник-тест-0412-1530"
	# Проверка
	Тогда остаток товара "Чайник-тест-0412-1530" равен 7
```

Здесь «создаю товар», «провожу приход» — **свои шаги** ([[12. Шаги, проверки и запись действий]]).

Ключевая деталь — **уникальное имя**. Если товар называется просто «Чайник», второй запуск создаст второй «Чайник», и выбор «по строке» станет неоднозначным. Уникальная часть (дата-время запуска, случайный номер) делает данные каждого запуска отдельными. В VA для этого есть шаги генерации и запоминания значений в переменные — имя генерируется один раз и дальше используется как `$ИмяТовара$`.

| Плюсы | Минусы |
| --- | --- |
| Сценарий самодостаточен, порядок запуска не важен | Сценарий длиннее |
| Не мешает другим сценариям | Данные копятся в базе — периодически базу всё равно пересоздают |

## Способ 3. Откат изменений

В **модульных и интеграционных** тестах на встроенном языке данные создаются внутри **транзакции**, которую в конце отменяют — база остаётся нетронутой ([[07. Модульные тесты своими руками]]). Для UI-сценариев этот способ не подходит: интерфейсные действия выполняются в другом сеансе и записываются как обычно.

## Какой способ выбрать

| Тесты | Обычно |
| --- | --- |
| Модульные и интеграционные на встроенном языке | Транзакция с откатом |
| UI-сценарии в регулярном прогоне | Эталонная база из `.dt` перед прогоном |
| Отдельные сценарии, которые должны работать на любой базе | Сценарий сам создаёт данные с уникальными именами |

Их часто комбинируют: эталонная база + сценарии, которые создают «одноразовые» данные поверх неё.

## Другие источники нестабильности

| Источник | Как избежать |
| --- | --- |
| **Текущая дата** | Не проверять «сегодня»; задавать дату документа явно; сравнивать с датой, запомненной в начале сценария |
| **Порядок строк** в списках | Искать строку по значениям, а не по позиции; задавать сортировку |
| **Скорость** | Не использовать фиксированные паузы — шаги ожидания окна или значения |
| **Окна от прошлых сценариев** | «Закрыть все окна» в `Контекст` |
| **Права тестового пользователя** | Отдельный тестовый пользователь с нужными ролями, а не администратор ([[01. Основы конфигурирования/19. Пользователи и Роли|19. Роли]]) |
| **Сохранённые настройки форм и отчётов** | Тестовый пользователь без «накопленных» пользовательских настроек; при необходимости — восстановление стандартных настроек в сценарии |

> [!tip] Тестовый пользователь
> Запускайте сценарии под специальным пользователем с **рабочей** ролью (например, «Менеджер»), а не под администратором. Так тесты заодно проверяют права — и не «проходят» там, где у реального пользователя была бы ошибка доступа.

> [!question]- Проверь себя
> 1. Что такое «мигающий» тест и чем он вреден?
> 2. Назовите три правила независимости тестов.
> 3. Как работает подход «эталонная база»?
> 4. Зачем при создании тестовых данных в сценарии нужны уникальные имена?
> 5. Почему для UI-сценариев не подходит откат транзакции?
>
> > [!success]- Ответы
> > 1. Тест, который то проходит, то падает без изменений в коде; ему перестают доверять, и автотесты теряют смысл.
> > 2. Известные данные на старте; независимость от других тестов и порядка; тест не портит данные для следующих.
> > 3. Тестовую базу перед каждым прогоном восстанавливают из эталонной выгрузки `.dt` с известными данными.
> > 4. Чтобы повторные запуски не создавали одинаковых элементов и выбор по строке был однозначным.
> > 5. Действия интерфейса выполняются в отдельном сеансе клиента тестирования и записываются в базу обычным образом — транзакцию сценария нельзя откатить.
