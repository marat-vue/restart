> [!abstract] Коротко
> **Модульный тест** — маленькая процедура, которая вызывает проверяемую функцию с известными данными и сравнивает результат с ожидаемым. Каждый тест строится по схеме **«Подготовка — Действие — Проверка»** (Arrange — Act — Assert). Самый простой инструмент в 1С — своя **тестовая внешняя обработка**: набор процедур-тестов и процедура `ПроверитьРавенство()`, которая пишет «ОК» или «ОШИБКА». **Интеграционный** тест проведения выполняется на сервере в **транзакции, которую потом отменяют**: создали и провели документ, проверили движения запросом, откатили — база осталась чистой. Чтобы код было удобно тестировать, расчёты выносят в **отдельные функции** без обращения к форме.

## Что такое модульный тест

**Модульный (unit) тест** проверяет **один маленький кусок** кода — одну функцию — отдельно от всего остального. Мы не открываем формы и не нажимаем кнопки: просто вызываем функцию с нужными параметрами и смотрим, что она вернула.

Аналогия: проверяя калькулятор, вы не разбираете его — вы набираете «2 × 150» и смотрите, показал ли он 300.

Модульные тесты:
- выполняются за **доли секунды** — можно запускать после каждой правки;
- точно показывают, **какая функция** сломалась;
- не зависят от интерфейса — не ломаются, если кнопку перенесли.

## Схема любого теста: Подготовка — Действие — Проверка

| Шаг | Что делаем | Пример |
| --- | --- | --- |
| **Подготовка** (Arrange) | Готовим входные данные | Количество = 3, Цена = 12.345 |
| **Действие** (Act) | Вызываем проверяемую функцию | `Сумма = РассчитатьСуммуСтроки(3, 12.345)` |
| **Проверка** (Assert) | Сравниваем результат с ожидаемым | `Сумма` должна быть 37.04 |

Тест, у которого нет проверки, ничего не тестирует — он только «запускает» код.

## Код, который удобно тестировать

Возьмём правило из раздела 04: сумма строки = количество × цена, с округлением до копеек ([[04. Программирование управляемых форм/10. Пересчёт строк и итога товаров|10. Пересчёт строк]]). Если формула записана прямо внутри обработчика формы — проверить её отдельно невозможно: обработчик требует открытую форму и текущую строку таблицы.

Поэтому расчёт выносят в **отдельную функцию**, которая получает значения параметрами и возвращает результат. Лучше всего — в общий модуль с флажками «Клиент» и «Сервер», чтобы ей пользовались и форма, и модуль объекта ([[02. Программирование/26. Общие модули и контекст выполнения|26. Общие модули]]):

```1C
// Общий модуль РасчетыКлиентСервер (Клиент, Сервер)

// Сумма строки товаров с округлением до копеек.
Функция РассчитатьСуммуСтроки(Количество, Цена) Экспорт
	Возврат Окр(Количество * Цена, 2);
КонецФункции

// Сумма со скидкой: от 100 штук включительно — 5%.
Функция СуммаСоСкидкой(Количество, Цена) Экспорт
	Сумма = РассчитатьСуммуСтроки(Количество, Цена);
	Если Количество >= 100 Тогда
		Сумма = Окр(Сумма * 0.95, 2);
	КонецЕсли;
	Возврат Сумма;
КонецФункции
```

> [!tip] Правило тестируемого кода
> Функция, которая **получает всё нужное параметрами** и **возвращает результат**, не читая форму, базу и глобальные переменные, тестируется одной строкой. Такие функции называют «чистыми». Чем больше логики в них, тем проще тестировать.

Если в учебной базе нет общего модуля для экспериментов, функции можно положить прямо в модуль тестовой обработки — для изучения техники это не важно.

## Тестовая обработка

Создаём внешнюю обработку `ТестыКупец` — так же, как песочницу из раздела алгоритмов ([[06. Алгоритмы для 1С/01. Что такое алгоритм и как решать задачи|01. Песочница]]): форма, команда «Запустить тесты», обработчик на клиенте.

```1C
&НаКлиенте
Процедура ЗапуститьТесты(Команда)
	Пройдено = 0;
	Упало = 0;

	ВыполнитьТест("Тест_СуммаСтроки_ЦелыеЧисла", Пройдено, Упало);
	ВыполнитьТест("Тест_СуммаСтроки_Округление", Пройдено, Упало);
	ВыполнитьТест("Тест_Скидка_ГраницаСнизу", Пройдено, Упало);
	ВыполнитьТест("Тест_Скидка_НаГранице", Пройдено, Упало);

	Сообщить(СтрШаблон("Итого: пройдено %1, упало %2", Пройдено, Упало));
КонецПроцедуры
```

### Процедура проверки

```1C
// Сравнивает фактическое значение с ожидаемым; при расхождении вызывает исключение.
&НаКлиенте
Процедура ПроверитьРавенство(Фактическое, Ожидаемое, Описание = "")
	Если Фактическое <> Ожидаемое Тогда
		ВызватьИсключение СтрШаблон("%1: ожидалось %2, получено %3",
			Описание, XMLСтрока(Ожидаемое), XMLСтрока(Фактическое));
	КонецЕсли;
КонецПроцедуры

// Запускает тест по имени процедуры и считает результат.
&НаКлиенте
Процедура ВыполнитьТест(ИмяТеста, Пройдено, Упало)
	Попытка
		Выполнить(ИмяТеста + "()");
		Пройдено = Пройдено + 1;
		Сообщить("ОК      " + ИмяТеста);
	Исключение
		Упало = Упало + 1;
		Сообщить("ОШИБКА  " + ИмяТеста + " — " + КраткоеПредставлениеОшибки(ИнформацияОбОшибке()));
	КонецПопытки;
КонецПроцедуры
```

| Код | Зачем |
| --- | --- |
| `ВызватьИсключение` при расхождении | Тест «падает» в момент первой неудачной проверки — дальше выполнять бессмысленно |
| `Выполнить(ИмяТеста + "()")` | Вызвать процедуру по имени из строки — так список тестов задаётся одной строкой на тест ([[02. Программирование/27. Ошибки и сообщения пользователю|27. Ошибки]]) |
| `Попытка … Исключение` | Падение одного теста не останавливает остальные |
| Счётчики `Пройдено`, `Упало` | Итоговая строка — сразу видно, всё ли в порядке |

> [!info] О `Выполнить`
> В рабочем коде `Выполнить()` с произвольной строкой — плохая практика: через неё можно выполнить любой код ([[05. Профессиональная разработка/11. Стандарты кода и самопроверка|11. Безопасность]]). В тестовой обработке, где строки — имена наших же процедур, это допустимо. Если не хочется использовать `Выполнить`, вызывайте тесты напрямую внутри своих `Попытка`.

### Сами тесты

```1C
&НаКлиенте
Процедура Тест_СуммаСтроки_ЦелыеЧисла() Экспорт
	// Подготовка
	Количество = 2;
	Цена = 150;
	// Действие
	Сумма = РасчетыКлиентСервер.РассчитатьСуммуСтроки(Количество, Цена);
	// Проверка
	ПроверитьРавенство(Сумма, 300, "2 × 150");
КонецПроцедуры

&НаКлиенте
Процедура Тест_СуммаСтроки_Округление() Экспорт
	ПроверитьРавенство(РасчетыКлиентСервер.РассчитатьСуммуСтроки(3, 12.345), 37.04, "3 × 12.345");
КонецПроцедуры

&НаКлиенте
Процедура Тест_Скидка_ГраницаСнизу() Экспорт
	ПроверитьРавенство(РасчетыКлиентСервер.СуммаСоСкидкой(99, 10), 990, "99 штук — без скидки");
КонецПроцедуры

&НаКлиенте
Процедура Тест_Скидка_НаГранице() Экспорт
	ПроверитьРавенство(РасчетыКлиентСервер.СуммаСоСкидкой(100, 10), 950, "100 штук — скидка 5%");
КонецПроцедуры
```

Тесты на 99 и 100 — это граничные значения из [[04. Техники тест-дизайна]]. Если кто-то поменяет условие на `Количество > 100`, тест `Тест_Скидка_НаГранице` сразу упадёт.

Вывод при запуске:

```text
ОК      Тест_СуммаСтроки_ЦелыеЧисла
ОК      Тест_СуммаСтроки_Округление
ОК      Тест_Скидка_ГраницаСнизу
ОК      Тест_Скидка_НаГранице
Итого: пройдено 4, упало 0
```

Если сломать округление (убрать `Окр`), увидим:

```text
ОК      Тест_СуммаСтроки_ЦелыеЧисла
ОШИБКА  Тест_СуммаСтроки_Округление — 3 × 12.345: ожидалось 37.04, получено 37.035
...
Итого: пройдено 3, упало 1
```

### Как называть тесты

Имя теста — это описание проверки. Удобный шаблон: `Тест_ЧтоПроверяем_ПриКакомУсловии`. По имени упавшего теста должно быть понятно, что сломалось, без чтения кода.

## Интеграционный тест: проверяем проведение

Модульный тест проверяет формулу. Но важнее убедиться, что **документ проводится и пишет правильные движения**. Для этого нужно работать с базой — значит, на **сервере**.

Проблема: тест создаёт и проводит документ — после теста в базе останется мусор. Решение — выполнить всё **внутри транзакции и отменить её** ([[02. Программирование/28. Транзакции и блокировки|28. Транзакции]]): документ создастся, проведётся, мы проверим движения, а `ОтменитьТранзакцию()` вернёт базу в исходное состояние.

```1C
&НаКлиенте
Процедура Тест_Проведение_ЗаписываетПродажи() Экспорт
	Результат = ПроверитьПроведениеНаСервере();
	ПроверитьРавенство(Результат, "", "Проведение накладной");
КонецПроцедуры

// Возвращает пустую строку, если всё в порядке, иначе — описание ошибки.
&НаСервереБезКонтекста
Функция ПроверитьПроведениеНаСервере()

	НачатьТранзакцию();
	Попытка
		// Подготовка: известные данные
		Товар = Справочники.Номенклатура.НайтиПоНаименованию("Чайник");
		Покупатель = Справочники.Контрагенты.НайтиПоНаименованию("Ромашка");
		Если Товар.Пустая() Или Покупатель.Пустая() Тогда
			ОтменитьТранзакцию();
			Возврат "В тестовой базе нет товара «Чайник» или покупателя «Ромашка»";
		КонецЕсли;

		Накладная = Документы.РасходнаяНакладная.СоздатьДокумент();
		Накладная.Дата = ТекущаяДатаСеанса();
		Накладная.Покупатель = Покупатель;
		Строка = Накладная.Товары.Добавить();
		Строка.Товар = Товар;
		Строка.Количество = 2;
		Строка.Цена = 150;
		Строка.Сумма = 300;

		// Действие
		Накладная.Записать(РежимЗаписиДокумента.Проведение);

		// Проверка: движения в регистре продаж
		Запрос = Новый Запрос(
		"ВЫБРАТЬ
		|	СУММА(П.Количество) КАК Количество,
		|	СУММА(П.Сумма) КАК Сумма
		|ИЗ
		|	РегистрНакопления.Продажи КАК П
		|ГДЕ
		|	П.Регистратор = &Ссылка");
		Запрос.УстановитьПараметр("Ссылка", Накладная.Ссылка);
		Выборка = Запрос.Выполнить().Выбрать();
		Выборка.Следующий();

		Ошибка = "";
		Если Выборка.Количество <> 2 Или Выборка.Сумма <> 300 Тогда
			Ошибка = СтрШаблон("Ожидались движения 2 шт. на 300, получено %1 шт. на %2",
				XMLСтрока(Выборка.Количество), XMLСтрока(Выборка.Сумма));
		КонецЕсли;

		ОтменитьТранзакцию();   // база возвращается в исходное состояние
		Возврат Ошибка;

	Исключение
		ОтменитьТранзакцию();
		Возврат "Исключение: " + КраткоеПредставлениеОшибки(ИнформацияОбОшибке());
	КонецПопытки;

КонецФункции
```

| Шаг | Что происходит |
| --- | --- |
| `НачатьТранзакцию()` | Все изменения дальше — «черновые» |
| Поиск товара и покупателя | Тест опирается на **известные** данные тестовой базы |
| Создание и проведение | То же, что сделал бы пользователь, но кодом |
| Запрос к регистру по регистратору | Проверяем именно движения этого документа |
| `ОтменитьТранзакцию()` | Документ и движения исчезают — база чистая для следующего запуска |

Если в проведении накладной уже есть контроль остатков ([[05. Профессиональная разработка/02. Контроль остатков и блокировки|02. Контроль остатков]]), сначала в той же транзакции создайте и проведите приходную накладную на нужное количество — иначе тест упадёт на нехватке товара, и это будет ошибка теста, а не программы.

Так же проверяют повторное проведение (провести дважды — сумма движений не удвоилась), отмену проведения (`Записать(РежимЗаписиДокумента.ОтменаПроведения)` — движений 0) и запрет проведения с неверными данными (ожидаем исключение).

> [!warning] Только на тестовой базе
> Даже с откатом транзакции запускаем интеграционные тесты на **копии** базы: ошибка в тесте (например, забытый `ОтменитьТранзакцию`) может оставить данные.

## Что тестировать модульно в первую очередь

| Кандидат | Почему |
| --- | --- |
| Формулы расчёта (суммы, скидки, налоги) | Ошибка в формуле портит все документы |
| Правила проверки (`ДанныеКорректны()`) | Легко проверить все ветки `Если` |
| Функции разбора и преобразования (JSON, строки, даты) | Много краевых случаев |
| Проведение ключевых документов | Ошибка в движениях дороже всего |
| Исправленные дефекты | Тест гарантирует, что дефект не вернётся |

> [!tip] Тест на каждый исправленный дефект
> Нашли и исправили ошибку — напишите тест, который её воспроизводит. Если когда-нибудь ошибка вернётся (регрессия), тест сразу это покажет.

> [!question]- Проверь себя
> 1. Из каких трёх шагов состоит модульный тест?
> 2. Почему формулу из обработчика формы трудно протестировать и что с этим делать?
> 3. Зачем в интеграционном тесте проведения нужна транзакция с отменой?
> 4. Какие тесты на скидку «от 100 штук» напишете по технике граничных значений?
>
> > [!success]- Ответы
> > 1. Подготовка, действие, проверка.
> > 2. Обработчику нужна открытая форма и текущая строка. Вынести формулу в отдельную функцию с параметрами (например, в общий модуль «Клиент, Сервер»).
> > 3. Чтобы созданный и проведённый тестом документ не остался в базе: после проверки изменения откатываются.
> > 4. 99 штук — без скидки; 100 — со скидкой (можно ещё 101).
