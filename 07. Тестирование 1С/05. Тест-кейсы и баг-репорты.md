> [!abstract] Коротко
> **Тест-кейс** — пошаговая инструкция проверки: название, предусловия, шаги, ожидаемый результат. Хороший тест-кейс проверяет **одно** поведение и может быть выполнен **другим человеком** без вопросов. **Чек-лист** — короткий список проверок без подробных шагов. **Баг-репорт** — описание найденного дефекта: заголовок «что, где, когда», шаги воспроизведения, ожидаемый и фактический результат, окружение, серьёзность, вложения (скриншот, текст ошибки). Хороший баг-репорт позволяет разработчику повторить ошибку с первого раза.

## Тест-кейс: подробная инструкция проверки

Тест-кейс пишут так, чтобы **любой** человек — коллега, новый тестировщик, вы сами через полгода — мог выполнить проверку и однозначно сказать, пройдена она или нет.

### Пример хорошего тест-кейса

| Поле | Значение |
| --- | --- |
| **Номер** | ТК-012 |
| **Название** | Расходная накладная не проводится без покупателя |
| **Предусловия** | Пользователь с ролью «Менеджер». В справочнике есть товар «Чайник» |
| **Шаги** | 1. Открыть «Торговый учёт → Расходные накладные». 2. Нажать «Создать». 3. Поле «Покупатель» оставить пустым. 4. На вкладке «Товары» добавить строку: «Чайник», количество 1, цена 150. 5. Нажать «Провести и закрыть» |
| **Ожидаемый результат** | Появилось сообщение «Выберите покупателя». Форма не закрылась. Документ не записан |
| **Приоритет** | Высокий |

### Признаки хорошего тест-кейса

| Признак | Плохо | Хорошо |
| --- | --- | --- |
| Проверяет одно поведение | «Проверить накладную» | «Накладная не проводится без покупателя» |
| Конкретные шаги | «Заполнить документ» | «Добавить строку: Чайник, 1, 150» |
| Конкретные данные | «Ввести количество» | «Ввести количество 2» |
| Однозначный ожидаемый результат | «Всё работает» | «Сумма строки = 300» |
| Независимый | Опирается на документ, созданный в другом тест-кейсе | Сам создаёт нужные данные или явно указывает их в предусловиях |

> [!warning] «Всё работает» — не ожидаемый результат
> Если по ожидаемому результату нельзя однозначно сказать «прошёл / не прошёл», тест-кейс бесполезен: двое исполнителей поймут его по-разному.

## Чек-лист: короткий список проверок

Подробные тест-кейсы писать долго. Для небольших доработок часто хватает **чек-листа** — списка проверок одной строкой без детальных шагов. Его используют, когда исполнитель хорошо знает программу.

**Чек-лист для доработки «пересчёт суммы строки в расходной накладной»:**

- [ ] Ввод количества пересчитывает сумму строки
- [ ] Ввод цены пересчитывает сумму строки
- [ ] Сумма округляется до копеек (3 × 12.345 = 37.04)
- [ ] Итог товаров обновляется после изменения строки
- [ ] Итог обновляется после удаления строки
- [ ] Пустая таблица — итог 0
- [ ] При записи из обработки (без формы) суммы тоже пересчитываются
- [ ] Открытие старого документа не меняет его суммы
- [ ] Под ролью «Менеджер» всё работает так же

Чек-лист отлично сочетается с техниками тест-дизайна ([[04. Техники тест-дизайна]]): каждая граница или комбинация из таблицы решений — строчка чек-листа.

## Баг-репорт: как сообщить об ошибке

Нашли дефект — нужно описать его так, чтобы разработчик **повторил ошибку с первого раза** и понял, что именно не так. Плохой баг-репорт — это переписка на день: «а как вы это сделали? а какой документ? а под каким пользователем?».

### Плохо и хорошо

**Плохо:**

> Накладная не работает, помогите срочно!!!

Что не работает? Какая накладная? Что вы делали? Что ожидали?

**Хорошо:**

| Поле | Значение |
| --- | --- |
| **Заголовок** | Расходная накладная: сумма строки не пересчитывается при изменении цены |
| **Шаги воспроизведения** | 1. Создать расходную накладную. 2. Добавить строку: «Чайник», количество 2, цена 150 — сумма 300. 3. Изменить цену на 200, нажать `Tab` |
| **Ожидаемый результат** | Сумма строки = 400 |
| **Фактический результат** | Сумма осталась 300. При изменении количества сумма пересчитывается правильно |
| **Окружение** | База «Купец (тест)», платформа 8.5.1.1150, тонкий клиент, пользователь «Менеджер Иванов» |
| **Серьёзность** | Высокая: в документ попадают неверные суммы |
| **Приоритет** | Высокий |
| **Вложения** | Скриншот формы после шага 3 |

### Из чего состоит баг-репорт

| Поле | Зачем | Совет |
| --- | --- | --- |
| **Заголовок** | Чтобы по одной строке понять суть | Формула «Что — где — при каком условии» |
| **Шаги воспроизведения** | Чтобы разработчик повторил | Нумерованные, с конкретными данными, начиная с открытия формы |
| **Ожидаемый результат** | Что должно было быть | Со ссылкой на требование, если есть |
| **Фактический результат** | Что получилось | Точный текст ошибки — скопированный, а не пересказанный |
| **Окружение** | Где воспроизводится | База, версия платформы и конфигурации, клиент, пользователь и его роли |
| **Серьёзность** | Насколько вредит | См. таблицу ниже |
| **Вложения** | Доказательства | Скриншот, текст ошибки, файл, видео |

### Серьёзность и приоритет — не одно и то же

| | Серьёзность (severity) | Приоритет (priority) |
| --- | --- | --- |
| Вопрос | Насколько дефект вредит работе программы? | Насколько срочно исправлять? |
| Кто определяет | Тестировщик | Руководитель проекта, заказчик |

Уровни серьёзности:

| Уровень | Что значит | Пример в 1С |
| --- | --- | --- |
| **Блокирующий** | Работать невозможно | База не открывается после обновления |
| **Критический** | Ключевая функция не работает или портит данные | Проведение задваивает движения |
| **Значительный** | Функция работает неправильно, но есть обходной путь | Сумма не пересчитывается при смене цены — можно пересчитать кнопкой |
| **Незначительный** | Мелкое неудобство | Неудобный порядок полей |
| **Косметический** | Опечатка, оформление | Опечатка в заголовке колонки |

Они могут расходиться: опечатка в названии компании на печатной форме — косметический дефект, но с **высоким** приоритетом, если завтра печатать договоры для крупного клиента.

### Как собрать информацию для баг-репорта в 1С

| Что нужно | Где взять |
| --- | --- |
| Текст ошибки | Окно ошибки → «Подробно» → скопировать текст: модуль, номер строки, стек |
| Версия платформы | «Справка → О программе» |
| Пользователь и роли | Конфигуратор: «Администрирование → Пользователи» |
| Что происходило в базе | Журнал регистрации ([[01. Основы конфигурирования/28. Резервные копии и обслуживание базы|28. Журнал регистрации]]) |
| Ссылка на документ | ПКМ по документу → «Получить ссылку» — коллега откроет тот же документ |

> [!tip] Минимальный пример
> Перед отправкой баг-репорта попробуйте найти **самый короткий** путь к ошибке: «на любом новом документе с одной строкой», а не «на документе №1543 от 15.03 у клиента Ромашка». Минимальный пример быстрее исправляют.

> [!question]- Проверь себя
> 1. Назовите четыре обязательные части тест-кейса.
> 2. Чем чек-лист отличается от тест-кейса и когда его достаточно?
> 3. Что должно быть в баг-репорте, чтобы разработчик повторил ошибку с первого раза?
> 4. Приведите пример дефекта с низкой серьёзностью, но высоким приоритетом.
>
> > [!success]- Ответы
> > 1. Название, предусловия, шаги, ожидаемый результат.
> > 2. Чек-лист — короткий список проверок без детальных шагов; достаточен для небольших доработок, когда исполнитель знает программу.
> > 3. Конкретные шаги воспроизведения с данными, ожидаемый и фактический результат, окружение (база, версия, пользователь), точный текст ошибки.
> > 4. Опечатка в реквизитах компании на печатной форме перед важной отгрузкой.
